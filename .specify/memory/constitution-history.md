# Barebones Constitution — 개정 이력

`constitution.md`의 개정 이력. **규칙 본문은 여기 없다.**

분리한 이유: 원칙은 매 세션 읽히고 이력은 "이 규칙 왜 이래?"를 물을 때만 열린다.
읽히는 빈도가 정반대인데 한 파일에 있으면, 거의 안 읽히는 부분이 항상 같이 실린다.

기록 대상은 **규칙이 실제로 바뀐 변경**뿐이다. 오타·렌더링·표 정렬처럼 규칙이 그대로인 수정은
버전도 올리지 않고 여기 남기지도 않는다 (constitution Governance 참조).

각 항목이 답해야 하는 질문은 "언제 바꿨나"가 아니라 **"왜 그때 그렇게 판단했나"**다.

## 1.3.0 — 2026-08-04

**변경**

- **V(A-5) 신설** — 객체는 명시적으로 만든다(객체 spread 금지). 기존 V~X를 VI~XI로 재번호
- A-3-D 수정 — 드라이버 전용·선택 옵션의 "끈 상태"를 **키 생략에서 `undefined` 값으로** 변경

**이유 — 왜 성능이 아니라 읽는 흐름인가**

객체 spread는 동작상 아무 문제가 없다. 금지하는 이유는 **읽는 사람의 흐름**이다.
`{ ...base, logging }`을 만나면 "이 객체에 뭐가 들어 있지"를 확인하러 `base`를 찾아가야 하고,
`base`가 또 spread면 다시 따라간다. 객체 하나의 모양을 알기 위해 파일을 몇 번 오가게 되고,
그 왕복이 읽던 맥락을 끊는다.

`...(cond ? { x } : {})`가 특히 나쁘다. 필드가 **있을 수도 없을 수도** 있어서 타입 선언만으로는
실제 모양을 알 수 없다. 실제로 이 저장소에 그런 코드가 있었고(`database.config.ts`의 `schema`/`ssl`),
"이 옵션 객체에 무슨 키가 들어가는가"를 답하려면 조건 두 개를 따라가야 했다.

**A-3-D를 함께 고친 이유** — 조건부 spread를 없애려면 "끈 상태"를 표현할 방법이 필요했다.
세 가지를 검토했다.

1. `ssl: false` — 기각. 드라이버마다 falsy 해석이 갈릴 수 있어서 A-3-D가 원래 금지한 것이다.
2. 객체를 만든 뒤 조건부 대입 — TypeORM 옵션이 큰 유니온 타입이라 좁히지 않으면 대입이 안 된다.
3. **`undefined` 값** — 채택. 모든 드라이버에서 "키가 없는 것"과 동일하게 취급되고,
   무엇보다 **객체 모양이 코드에 그대로 보인다.**

대가는 `expect(options).not.toHaveProperty('ssl')` 같은 단언이 성립하지 않는 것이다.
테스트를 `expect(options.ssl).toBeUndefined()`로 바꿨다 — 검증하려던 것("SSL이 꺼져 있다")은
그대로이고, 표현만 실제 구현에 맞춘 것이다.

**`Object.assign` 예외를 명시한 이유**

`Object.assign`은 이 lint 룰을 통과한다. 그런데 읽는 흐름을 끊는 정도는 spread와 같으므로
우회로로 쓰면 규칙이 무의미해진다. 실제로 **한 곳에서 필요했다** — `jest.mock('prom-client')`가
서드파티 모듈 표면 전체를 다시 내보내면서 하나만 교체한다. 그 구조는 우리가 정의한 것이 아니라
필드를 적을 수가 없고, 손으로 나열하면 버전이 올라갈 때마다 조용히 빠진 export가 생긴다.
그래서 **"서드파티 표면 재수출"만 예외**로 못 박고, 그 외에는 쓰지 않는다고 적었다.
예외를 적지 않으면 lint를 통과하는 우회로가 사실상 허용된 것이 된다 — 1.2.0에서
"규칙이 버그를 승인한다"고 지적한 것과 같은 종류의 빈틈이다.

## 1.2.0 — 2026-08-04

**변경**

- **A-3 예외 1에 의무 두 개 추가** — `.env` 로딩 순서 보장, 결정된 플래그의 부팅 로그
- A-3-S 신설 (TLS 검증을 끄지 않는다) / A-3-P 신설 (프록시 홉 수를 명시한다)
- A-1-P-U 신설 (유니크 위반은 포트 에러로 번역한다, check-then-act 금지)
- C-1에 soft delete + partial unique 인덱스 항목 추가
- E-1에 네 항목 추가 — 로그 제외 경로를 상수에서 파생, `headersSent` 가드,
  조용히 실패하는 API 금지

**이유 — 규칙이 버그를 승인하고 있었다**

파생 프로젝트(CESEEM)의 전수 리뷰 13건을 이 스캐폴드에 대조한 결과 **9건이 그대로 해당**했다.
barebones가 상류이므로 당연한 결과지만, 그중 하나는 성격이 달랐다.

`.env` 파일에 `PROMETHEUS_ENABLED=true`를 써도 metrics 모듈이 켜지지 않는다. 원인은 JS 모듈
평가 순서다 — `app.module.ts`의 모듈 본문이 `ConfigModule`의 `.env` 로드보다 **먼저** 실행된다.
`docker compose`에서는 값이 OS 환경변수로 오므로 우연히 동작하고, **`.env` 파일 경로만 조용히
깨진다.** 게다가 `isFeatureEnabled`는 `'true'`만 참으로 보므로 결과는 "기본값으로 켜짐"이 아니라
**모듈이 전부 빠진 상태**이고, 그래도 앱은 정상 부팅한다.

문제는 A-3 예외 1이 이 패턴을 **정당한 예외로 승인하고 있었다는 점**이다. "DI 컨테이너가 없어서
`process.env`를 읽는다"는 이유는 맞지만, **그 대가(`.env` 파일이 안 읽힌다)를 적지 않았다.**
어제 CESEEM 일지에 "코드를 짜다가 규칙을 발견하면 즉시 constitution에 반영한다"를 패턴으로
적었는데, 그 반영이 **정당화만 하고 대가를 빠뜨린 사례**가 나온 것이다. 그래서 예외를 없애는
대신 **의무 두 개를 붙였다** — 순서 보장과 부팅 로그. 예외 자체는 여전히 필요하다.

**이유 — 리뷰 처방을 그대로 받지 않았다**

리뷰는 BullMQ 연결에 `db`와 `keyPrefix`가 빠졌다고 지적했다. `db`는 맞지만 **`keyPrefix`는
넘기면 안 된다** — BullMQ는 ioredis의 `keyPrefix`를 명시적으로 거부한다
(`'BullMQ: ioredis does not support ioredis prefixes, use the prefix option instead.'`).
키 이름을 Lua 스크립트가 계산하기 때문이다. 네임스페이스는 이미 `BullModule`의 `prefix`가
담당하고 있었다. 소스를 확인하지 않고 처방을 따랐으면 큐가 부팅에서 깨졌다.

**이유 — 세 개의 테스트가 버그를 명세로 못박고 있었다**

`delByPrefix`, BullMQ 연결 옵션, `logger.interceptor`의 `userId`. 셋 다 테스트가 있었고
셋 다 통과했다. 이유가 같다 — **mock에 넘긴 인자만 단언했기** 때문이다. BullMQ 테스트의 이름은
아예 `'extracts only host, password, and port'`였다. 1.1.0에서 D-1-M을 신설한 판별법
("구현을 통째로 mock으로 바꿔도 통과하는가?")이 여기서도 그대로 적용됐고,
`delByPrefix`는 ioredis의 `keyPrefix` 적용 규칙을 실제로 확인해서 **무엇을 넘겨도 0건**임을
증명한 뒤 지웠다(SCAN의 MATCH에는 prefix가 안 붙고, DEL에는 또 붙는다).

**이유 — E-1에 몰린 네 항목의 공통점**

로그 제외 경로 오류, `headersSent` 미확인, 조용히 실패하는 `delByPrefix`, 그리고 위의 플래그
타이밍. 전부 **작동하는 것처럼 보이는데 안 하고 있는** 종류다. 예외도 실패도 없으므로
테스트·리뷰·모니터링 어디에도 걸리지 않는다. 그래서 개별 수정과 별개로
"조용한 실패를 시끄러운 실패로 바꾼다"를 규칙 문장으로 남겼다.

## 1.1.0 — 2026-08-04

**변경**

- A-1-P에 **A-1-P-C(포트 계약 위반은 즉시 던진다)** 추가, 토큰 생성 방식을
  `createRepositoryToken` + `PortOf`로 변경
- A-1-R: lint 차단 범위를 `test/**`까지 확장
- A-3: **검증과 소비는 같은 파서를 공유한다** 조항 추가
- B-3: 호출부 버그는 500이 맞다는 항목 추가
- D-1: **D-1-M(mock이 증명할 수 없는 것은 실제 DB로)** 신설
- E-1: 정상 종료에서 `process.exit()` 금지, 요청 식별자 응답 헤더 노출 추가

**이유**

1.0.0 직후 코드 리뷰에서 10건이 나왔고, 그중 6건이 **규칙의 빈틈**이었다.
가장 뼈아픈 것은 상위 4건이 같은 뿌리였다는 점이다 — `IRepository<T>` 계약이 실제 TypeORM
동작보다 느슨하게 선언돼 있었고, **그걸 잡아낼 유일한 대상(Repository)을 단위 테스트가
mock하고 있었다.** 그래서 게이트 6개가 전부 초록불인 상태로 다음이 통과했다.

- `findOne({})` — 스펙에서는 통과하고 실제 DB에서는 예외 (`You must provide selection conditions...`)
- `update(where, {})` — 스펙은 `1`을 단언하는데 실제로는 `UpdateValuesMissingError`
- `insert()` — 같은 키로 두 번 부르면 유니크 위반이 아니라 **기존 행을 덮어씀** (`save()`의 upsert 성질)
- `where: { ownerId: undefined }` — 조건이 조용히 사라져 **전체 행 반환**

이건 D-2가 이미 금지한 "검증 대상 로직을 통째로 mock해서 사실상 mock을 테스트하는 것"인데,
그 조항이 **"어떤 종류의 주장이 mock으로 증명 불가한가"를 말해주지 않아서** 걸러지지 않았다.
그래서 D-1-M을 판별법(`"구현을 통째로 mock으로 바꿔도 통과하는가?"`)과 함께 신설하고,
해당 검증들을 `test/persistence.e2e-spec.ts`로 옮겼다.

A-3의 파서 공유 조항도 같은 성격이다. `CORS_ORIGINS`를 `invalid('*')`로만 막았는데
런타임은 쉼표로 쪼갠 목록을 봤다. 그래서 `'https://app.example.com,*'`가 production 검증을
통과한 뒤 전체 origin 허용 + credentials 허용이 됐다. **어제 CESEEM에서 발견한
`allow('')` 구멍과 정확히 같은 실수** — Joi 규칙이 값의 표면 형태만 보고 실제 소비 지점과
어긋난 것이다. 한 번은 사고, 두 번은 패턴이라 조항으로 올렸다.

토큰 방식을 바꾼 이유는 `provideRepositoryPort(TOKEN, Entity)`의 제네릭이 인자에서 추론되지
않아 **잘못 짝지어도 컴파일이 통과**했기 때문이다(실제로 확인). 새 아키텍처의 유일한 배선
지점이 안전해 보이면서 아무것도 보장하지 않는 상태였다. 토큰과 엔티티를 함께 만들고
주입 타입을 토큰에서 파생시키면(`PortOf`) 어긋날 방법이 없어진다.

E-1의 `process.exit()` 조항은 리뷰에서 유일하게 재현하지 못한 항목이다. pino transport가
워커 스레드에서 비동기 flush한다는 사실은 확실하므로 조항으로 남겼다 — 종료 로그는
"유실될 수도 있다"로 두기에 너무 중요하다.

## 1.0.0 — 2026-08-04

**변경**

최초 작성. 파생 프로젝트에서 운용하며 확립된 규칙을 스캐폴드로 역이식하고,
영속화 포트(A-1-P)와 DB 교체 지점(A-3-D)을 이 저장소에서 새로 정의했다.

- A-1 계층 책임 분리, A-1-R(TypeORM 격리), A-1-W(얇은 래퍼 금지, 양방향)
- **A-1-P 신설** — 영속화 포트와 그것이 놓일 위치
- A-2 모듈 경계 / A-3 설정 단일 출처 / **A-3-D 신설**(DB 교체 지점) / A-4 생성물
- B-1 라우팅 / **B-2 OpenAPI 문서**(파생 프로젝트의 "Swagger 비범위"를 뒤집은 조항) /
  B-3 응답 형식 / B-4 입력 검증
- C-1 마이그레이션 / C-2 테스트 DB
- D-1~D-3 테스트 동반·금지 패턴·완료 게이트
- E-1 관측 가능성 / G-1 저장소 간 쓰기 순서 / H-1 트랜잭션 경계
- F-1~F-4 워크플로 / Governance

**이유 — 왜 포트를 Repository와 ORM 사이에 두었나**

"어떤 DB든 쓸 수 있게 `IRepository`로 의존성 역전을 하자"는 요구에서 출발했다.
그런데 파생 프로젝트에서 이미 기각된 안이 하나 있었다 —
**"기본 CRUD(`find` / `findOne` / `save`)는 범용으로 열고 복잡한 쿼리만 명명하자."**
기각 이유가 셋이었고, 그게 그대로 이 결정의 제약이 됐다.

1. **불변식이 사라진다.** 호출부가 `findOne({ where: { email } })`을 쓸 수 있게 되는 순간
   정규화는 선택사항이 된다. 유니크 인덱스가 정규화된 형태 기준이면 `A@B.com`으로 가입한 사용자를
   못 찾는다. 컴파일 에러도 테스트 실패도 아니고 고객 문의다.
   `select: false` 컬럼도 같다 — 필요한 필드가 `undefined`로 와서 엉뚱한 곳에서 터진다.
2. **"Repository를 안 열어봐도 된다"가 뒤집힌다.** 쿼리 모양이 파일 1개에서 N개 콜사이트로 흩어진다.
   Repository는 짧아지고 시스템은 덜 검색 가능해진다. 인덱스를 추가할 때 대상 쿼리를 못 찾는다.
3. **D-1이 검증할 것이 없어진다.** 패스스루의 spec은 `expect(mock.findOne).toHaveBeenCalledWith(options)`
   뿐이고, 그건 D-2가 금지한 "mock을 테스트하는 것"이다.

즉 **제네릭 조회 인터페이스를 Service가 볼 수 있는 위치에 두는 것은 A-1-W 위반**이다.
그런데 의존성 역전 자체는 하고 싶다. 두 요구가 충돌하는 것처럼 보였고, 실제로는 아니었다 —
**포트를 한 칸 아래에 두면 된다.**

```
Service  →  <Domain>Repository  →  IRepository<T>  →  Adapter  →  DB
         ↑ 도메인 시그니처만    ↑ 포트 경계
```

`FindCriteria`는 도메인 Repository **안에서만** 쓰이고 Service는 그 존재를 모른다.
A-1-W는 그대로 유효하고(방향 2가 "포트 타입을 공개 시그니처에 두지 않는다"로 바뀔 뿐),
ORM 교체 가능성은 얻는다. 이 위치 선택이 A-1-P의 전부다.

부수 효과로 **차단이 파생 프로젝트보다 강해졌다.** 거기서는 TypeORM이
`*.repository.ts`에도 있어야 했지만, 여기서는 도메인 Repository가 포트만 보므로
TypeORM을 세 곳(`common/persistence`, `config`, `database`)으로 완전히 몰아넣을 수 있다.
`eslint.config.mjs`의 차단 목록에 쿼리 옵션 타입과 연산자(`In`, `IsNull` 등)까지 넣은 것이 그 결과다.
위반 파일과 예외 파일 양쪽에서 실제 발동을 확인했다.

**이유 — 포트를 좁게 유지하는 조항을 같이 넣은 것**

포트가 있다는 사실만으로는 위 1~3번이 막히지 않는다. `FindCriteria`에 범위·부분일치·OR을
계속 추가하면 그것이 곧 ORM 쿼리 언어가 되고, 어댑터를 갈아탈 때 번역할 표면이 무한히 늘어난다.
그 시점에는 포트가 "TypeORM을 이름만 바꿔 다시 export한 것"이 된다 —
**구조의 비용은 다 내고 강제력은 0.** 그래서 "포트를 넓히지 않는다"와
"필요하면 어댑터에 이름 있는 메서드를 추가한다"를 A-1-P에 함께 못 박았다.

**이유 — H-1을 도입 전에 미리 쓴 것**

트랜잭션은 아직 없다. 그런데 포트에 트랜잭션 API를 넣지 않은 결정은 되돌리기 비싸므로
근거를 지금 남긴다. `EntityManager`를 포트에 노출하면 ORM 교체 가능성이 사라지고,
Service가 `DataSource`를 직접 잡으면 A-1-R과 충돌한다. 그래서 채택 예정안을
`typeorm-transactional`로 미리 적었다 — **포트와 어댑터 시그니처를 건드리지 않고**
Service가 경계를 선언할 수 있는 방식이라서다. 이 조항은 금지가 아니라 **도입 조건의 선언**이다.

**이유 — B-2를 파생 프로젝트와 반대로 쓴 것**

파생 프로젝트는 Swagger를 "의도적 비범위"로 뒀다(DTO에 `@ApiProperty`가 번지는 비용 대비 이득 없음).
스캐폴드는 반대다 — 어떤 API가 올지 모르는 시작점에서 문서 생성기를 빼두면,
필요해진 프로젝트마다 각자 붙이고 각자 다르게 붙인다. 대신 `APP_SWAGGER_ENABLED`로
노출을 끌 수 있게 했다. 끄는 수단이 없으면 "코드를 고쳐서 배포"가 유일한 방법이 된다.

**이유 — A-3에 Joi `allow()` 조항을 넣은 것**

production 강화 규칙을 얹으면서 실제로 새는 것을 확인했다.
base가 `Joi.string().allow('')`인 필드에 `then: Joi.string().min(1).required()`를 얹어도
빈 문자열이 **통과한다** — Joi가 길이 규칙보다 valids를 먼저 보기 때문이다.
"production에서는 빈 DB 비밀번호를 거부한다"는 규칙이 조용히 무효인 상태였고,
테스트를 먼저 써서 잡았다. `invalid('')`로 뒤집어야 한다는 것을 조항으로 남겼다 —
같은 패턴을 다음 환경변수에서 반복할 것이 확실하기 때문이다.
