# Barebones Constitution

이 문서는 **이 스캐폴드와, 이것으로 시작하는 모든 프로젝트가 지켜야 하는 불변 규칙**이다.
개별 기능의 `spec.md` / `plan.md` / `tasks.md`는 이 문서를 위반할 수 없다.
규칙을 바꿔야 한다면 코드보다 이 문서를 먼저 고치고, 변경 이유를 `constitution-history.md`에 남긴다.

각 원칙의 괄호 안 ID(`A-1`, `B-2` 등)는 안정적인 참조용이다. 스펙·플랜·태스크에서 이 ID로 근거를 인용한다.

> **이 저장소는 barebones-only다.** 도메인 모듈이 하나도 없고, 앞으로도 없다.
> 여기 있는 규칙은 "도메인을 어떻게 만들어야 하는가"의 **골격과 가드레일**이며,
> 실제 도메인은 이 스캐폴드로 파생시킨 프로젝트에 만든다.
> 그래서 이 문서에는 특정 업무 규칙·엔티티·인증 정책이 등장하지 않는다. 등장하면 그건 잘못 들어온 것이다.

## Core Principles

### I. 계층 책임 분리 (A-1)

| 계층           | 담는 것                                             | 담지 않는 것                         |
| -------------- | --------------------------------------------------- | ------------------------------------ |
| **Controller** | HTTP 관심사 — 라우팅, DTO 바인딩, 상태코드          | 비즈니스 로직, 쿼리                  |
| **Service**    | 비즈니스 **판단**과 트랜잭션 경계                   | 쿼리 작성, `Request`/`Response` 객체 |
| **Repository** | 테이블 접근과 **그 테이블을 다루는 데 필요한 지식** | 비즈니스 판단, 예외 던지기           |
| **Entity**     | 영속 모델                                           | 비즈니스 규칙                        |

**영속화 포트 (A-1-P)**

도메인 Repository는 ORM이 아니라 **포트에 의존한다.**

```
Service  →  <Domain>Repository  →  IRepository<T>  →  TypeOrmRepositoryAdapter  →  DB
         ↑                      ↑
  도메인 시그니처만       포트 경계 (여기가 유일하다)
```

- 계약은 `src/common/persistence/repository.port.ts`의 `IRepository<T>`다. TypeORM 타입이 없다.
- 구현체는 `src/common/persistence/`의 어댑터뿐이다. **ORM을 갈아탈 때 새로 쓰는 파일은 그것 하나다.**
- 주입 토큰은 `createRepositoryToken('NAME', Entity)`로 만든다. 토큰과 엔티티를 **한 번에 같이**
  만들기 때문에 둘이 어긋날 수 없다. 도메인 모듈은 `provideRepositoryPort(TOKEN)`으로 등록한다.
  - 토큰과 엔티티를 따로 받는 형태(`provideRepositoryPort(TOKEN, Entity)`)를 쓰지 않는다.
    잘못 짝지어도 컴파일이 통과해서, 런타임에 **다른 테이블을 조회하는 Repository**가 조용히 만들어진다.
- 주입 파라미터의 타입은 **토큰에서 파생시킨다** (`PortOf<typeof TOKEN>`). Nest의 `@Inject()`는
  선언한 타입을 검사하지 않으므로, 타입을 손으로 다시 쓰면 엔티티가 바뀔 때 주입 지점이 따라오지 않는다.
- **`IRepository<T>`를 도메인 밖으로 export하지 않는다.** 모듈이 `exports`에 넣는 것은
  도메인 Repository 클래스이고, 포트는 그 안에서만 쓰인다.

**포트 계약 위반은 즉시 던진다 (A-1-P-C)**

"조건이 사라져서 의도보다 많은 행에 닿는" 입력은 조용히 넘기지 않고 `RepositoryContractError`를 던진다.

- `where`의 값이 `undefined` — 필터 변수가 비었는데 조건만 사라진 경우.
  막지 않으면 `findMany({ where: { ownerId } })`가 **전체 행을 돌려준다.** 예외도 경고도 없이
  다른 사용자의 데이터가 나가는 종류의 사고다. 조건을 선택적으로 넣어야 한다면 **키 자체를 뺀다.**
- `findOne` / `update` / `remove`의 빈 `where` — 조건 없는 단건 조회·대량 갱신·전체 삭제.
- 어댑터는 `save()`가 아니라 `insert()`를 쓴다. `save()`는 upsert라 이미 있는 키로 부르면
  유니크 위반이 아니라 **기존 행을 조용히 덮어쓴다.** 중복 검사를 Service가 하는 구조(A-1)에서
  검사와 저장 사이에 경합이 생기면 먼저 저장된 데이터가 소실된다.
- 반대로 `update`의 **빈 `patch`는 예외가 아니다.** 갱신할 것이 없는 것은 "변경된 필드만 담는"
  흔한 정상 상태이므로 `0`을 돌려주는 no-op으로 처리한다.

**유니크 위반은 포트 에러로 번역한다 (A-1-P-U)**

- 어댑터가 드라이버별 신호(postgres `23505` / mysql·mariadb `1062`)를
  `UniqueConstraintError` **하나로** 바꾼다. 그 지식은 어댑터에만 있어야 한다 (A-1-R) —
  도메인이 에러코드를 알면 DB를 바꿀 때 도메인 코드가 따라 바뀐다.
- 알아보지 못한 에러는 **그대로 다시 던진다.** 유니크 위반으로 오분류하면 진짜 DB 장애가
  409로 나가서 클라이언트가 재시도하지 않는다.
- **Service가 `ConflictException`(409)으로 번역한다.** 번역하지 않으면 500이 되고,
  클라이언트는 "내 요청이 잘못됐다"와 "서버가 고장났다"를 구분할 수 없다.
- **"먼저 조회해서 있으면 거부"로 대체하지 않는다.** check-then-act는 DB가 강제하는 제약을
  애플리케이션이 흉내내는 것이고, 확인과 쓰기 사이의 간격 때문에 동시 요청에서 항상 깨진다.
  트랜잭션으로도 못 막는다 — 넣으려는 행이 아직 없어서 **잠글 대상이 없다.**
  진짜 방어선은 DB의 유니크 인덱스 하나뿐이고, 애플리케이션의 일은 **번역**이다.
  (사전 조회는 "정상 경로에서 예외를 안 타게 하는 최적화"로만 정당하다.)

> 이 조항들은 **mock으로 검증할 수 없다.** Repository를 mock하면 무엇이든 돌려주기 때문에
> "insert가 덮어쓰지 않는가", "빈 patch에서 무슨 일이 나는가"는 통과하지만 아무것도 증명하지 못한다.
> 실제 DB로 확인한다 (D-1).

**포트가 놓인 위치가 규칙의 전부다.** 포트는 **Repository와 ORM 사이**에 있고,
Service와 Repository 사이가 아니다. 한 칸만 올려서 Service가 `findOne({ where: ... })`를
직접 쓸 수 있게 되는 순간, 아래 A-1-R이 지키는 지식(정규화, `select: false` 처리)이
**선택사항**이 된다. 컴파일도 되고 테스트도 통과하고, 운영에서 조용히 틀린 결과가 나온다.

**포트를 넓히지 않는다.** `FindCriteria`에는 동등 비교와 `IN` / `IS NULL`만 있다.
범위·부분일치·OR을 추가하기 시작하면 이 타입이 곧 ORM 쿼리 언어가 되고,
어댑터를 갈아탈 때 번역해야 할 표면이 무한히 늘어난다. 그런 쿼리가 필요하면
**어댑터에 이름 있는 메서드를 추가한다** — 포트에 연산자를 추가하지 않는다.

**TypeORM 격리 (A-1-R)**

TypeORM 타입(주입 데코레이터, 쿼리 옵션, 결과 타입, 연산자)은 **아래 세 곳에만 존재한다.**

| 예외                        | 이유                                        |
| --------------------------- | ------------------------------------------- |
| `src/common/persistence/**` | 포트의 유일한 구현체가 사는 곳              |
| `src/config/**`             | 연결 옵션과 마이그레이션 CLI용 `DataSource` |
| `src/database/**`           | 마이그레이션 파일                           |

**이 규칙은 `yarn lint`가 강제한다.** `eslint.config.mjs`의 `no-restricted-imports`가
위 세 곳 밖에서 `InjectRepository` / `getRepositoryToken`과 `typeorm`의 주입·쿼리 표면을 금지한다.
위반하면 빌드가 실패하고 에러 메시지가 이 조항을 가리킨다.
예외를 늘려야 한다면 **먼저 이 표를 고치고 이유를 적는다.** lint 설정만 조용히 바꾸지 않는다.

**차단은 `test/**`에도 적용된다.** `src`만 검사하면 "e2e에서 직접 조회해서 검증"하는 우회로가
열리고, 그러면 도메인 Repository를 거치지 않는 테스트가 만들어져 정규화·`select` 규칙이 깨져도
초록불이 된다. 엔티티 정의 데코레이터(`@Entity`/`@Column`)는 쿼리 표면이 아니라 금지 목록에
없으므로, 테스트가 픽스처 엔티티를 정의하는 것은 그대로 가능하다.

**단, 이 방어는 절반짜리다** — 무엇을 못 막는지는 A-1-W 끝의 주석을 본다.

**얇은 래퍼 금지 (A-1-W)**

**어느 계층이든, 아래 계층 호출을 그대로 넘기기만 하는 메서드를 만들지 않는다.** 두 방향 모두다.

_방향 1 — Service → Repository_

```ts
// 금지 — 값을 더하지 않는다
findById(id: string) { return this.fooRepository.findById(id); }
```

조회만 필요한 호출부는 **Repository를 직접 주입받는다.** 의미 없는 통과 계층이 하나 끼면
"열어봐야 알맹이가 없다"는 학습이 생기고, 그러면 **알맹이가 있는 함수까지 안 열어보게 된다.**
의미 없는 층이 의미 있는 층의 신호를 죽인다.

Service에 남아야 하는 것은 판단이 있는 것뿐이다 — 중복 검사, 정책 적용, `null`을 404로 바꾸기 등.

_방향 2 — Repository → 포트_

```ts
// 금지 — 포트를 다시 export하는 것과 같다
findOne(criteria: FindCriteria<Foo>) { return this.port.findOne(criteria); }
```

**도메인 Repository 메서드는 도메인 값을 받고 도메인 결과를 돌려준다.**
`FindCriteria` / `WhereFilter` 같은 포트 타입을 공개 시그니처에 두지 않는다.
그게 새는 순간 A-1-P의 마지막 문단이 말한 상태가 된다.

메서드가 늘어나는 게 부담이면 답은 조건 노출이 아니라 **도메인 파라미터를 받는 메서드로 묶는 것**이다.
`findMany({ ownerId, search, page })` 하나가 쿼리 열두 가지를 흡수한다.
호출부는 의도를 말하고, 쿼리는 Repository가 정한다.

_판별법 (양방향 공통)_

> 메서드 몸통이 인자를 **그대로** 넘기고, **그 테이블을 아무것도 모르는 사람이 호출할 수 있으면** 패스스루다.

`findByEmail(email)`은 통과한다 — 정규화 규칙을 알아야 쓸 수 있다. `findOne(criteria)`는 걸린다.

> A-1-W는 **lint로 강제할 수 없다.** "이 메서드가 값을 더하는가"는 기계가 판단할 수 없어서
> 코드 리뷰와 명세 분석 단계의 몫이다.
>
> `eslint.config.mjs`가 TypeORM import를 막지만 그건 **절반짜리 방어**다.
> TypeScript는 구조적 타입이라, 어떤 Repository가 `findOne(criteria: FindCriteria<T>)`를
> 노출하면 호출부는 타입을 import하지 않고 객체 리터럴만 넘겨도 통과한다.
> lint는 타입이 **번지는** 것을 막을 뿐, 그런 시그니처를 갖는 것은 못 막는다. 그건 이 조항과 리뷰가 막는다.

**변환 함수와 적용 지점을 구분한다.** 문자열 정규화 같은 순수 변환은 재사용될 수 있으므로
`src/common/utils/`에 두어도 된다. 하지만 **"이 테이블은 정규화된 형태로 저장하고 조회한다"는
정책의 적용 지점은 Repository 안이어야 한다.** 함수를 공용으로 뺀 것과 호출부가 그 함수를
직접 부르는 것은 다른 문제다 — 후자를 허용하면 "한 경로만 빠뜨려도 깨진다"는 원래 문제로 돌아간다.
보장은 함수가 아니라 **"모든 경로가 그 함수를 통과한다"**에서 나온다.

### II. 모듈 경계 (A-2)

- 도메인 기능은 `src/<domain>/` 아래에 자체 NestJS 모듈로 만든다.
- 기술 인프라(외부 시스템 어댑터)는 `src/infra/<tech>/`에 둔다 (`redis`, `queue`, `metrics`).
- 횡단 관심사(필터/인터셉터/데코레이터/유틸/영속화 포트)는 `src/common/`에 둔다.
- **도메인 모듈은 다른 도메인 모듈의 내부를 직접 import하지 않는다.** 해당 모듈이 `exports`에
  명시한 것만 사용한다. `exports` 목록이 곧 **"이 모듈이 밖에 허용하는 것"의 선언**이다.
- 다른 도메인의 데이터를 **읽기만** 한다면 그 도메인의 `Repository`를 주입받는다.
  조회에는 지켜야 할 불변식이 없으므로 Service를 거칠 이유가 없다 (A-1-W).
- 다른 도메인의 데이터를 **만들거나 바꾼다면** 반드시 그 도메인의 `Service`를 거친다.
  불변식이 거기에만 있기 때문이다.
- **영속화 포트는 어떤 모듈도 export하지 않는다** (A-1-P).

### III. 설정 단일 출처 (A-3)

- 환경변수는 **반드시** `ConfigService`를 통해 읽는다. `process.env` 직접 접근 금지.
  - **예외 1**: 모듈 조립 시점(`@Module` 데코레이터의 `imports` 배열을 만드는 시점)에는 DI 컨테이너가
    아직 없어서 `ConfigService`를 주입받을 수 없다. 모듈을 켜고 끄는 feature flag에 한해
    `process.env` 직접 접근을 허용한다 (`app.module.ts`의 `REDIS_ENABLED` / `BULLMQ_ENABLED` /
    `PROMETHEUS_ENABLED`). 이 예외는 **모듈 포함 여부 판단에만** 적용된다.

    이 예외에는 **두 가지 의무가 따라온다.** 예외를 허용하기만 하고 아래를 적지 않으면
    규칙이 버그를 승인하게 된다.
    1. **`.env` 파일이 그 시점에 로드돼 있어야 한다.** `ConfigModule.forRoot({ envFilePath })`는
       모듈 본문보다 **나중에** 실행되므로, 아무 조치가 없으면 플래그는 `.env` 파일 값을 못 본다.
       OS 환경변수(`docker compose` / ECS)로 주는 경우만 우연히 동작한다.
       `main.ts`가 `./config/load-env`를 `AppModule`보다 **먼저 import**해야 하고,
       두 로더는 **같은 파일 목록**(`envFilePaths()`)을 공유해야 한다.
       함수 호출로는 해결되지 않는다 — `import`는 호이스팅되어 어떤 문장보다 먼저 평가된다.
    2. **결정된 값을 부팅 로그로 남긴다** (E-1). 이 경로의 실패는 예외를 던지지 않고
       **모듈이 조용히 빠진 상태로 정상 부팅**한다. "레디스는 되는데 메트릭만 404" 같은
       증상으로만 드러나므로, 조용한 실패를 시끄러운 실패로 바꾸는 것이 필수다.

  - **예외 2**: 마이그레이션 CLI 경로(`buildDataSourceOptionsFromEnv`)는 Nest 밖에서 실행된다.

- 새 환경변수를 추가하면 다음 세 곳을 **같은 커밋에서** 갱신한다:
  1. `src/config/env.validation.ts` (Joi 스키마 — production 강화 규칙 포함 여부 판단)
  2. `.env.example`
  3. `docker-compose.yml` (컨테이너에 필요한 값인 경우)
- 검증 실패는 **부팅 실패**다. "떴는데 설정이 비어서 런타임에 터지는" 상태보다 "안 뜨는" 상태가 낫다.
- production 강화 규칙을 base 스키마 위에 얹을 때는 **`allow()`가 남아 있는지 확인한다.**
  `Joi.string().allow('')`인 필드에 `min(1).required()`만 얹으면 `''`는 여전히 통과한다
  (Joi가 길이 규칙보다 valids를 먼저 본다). `invalid('')`로 명시적으로 뒤집어야 한다.
- **검증과 소비는 같은 파서를 공유한다.** 값이 런타임에 쪼개지거나 변환된다면
  검증도 **변환된 형태**를 대상으로 해야 한다. 원문 문자열만 검사하면 우회로가 생긴다.
  실제로 겪은 사례: `CORS_ORIGINS`를 `invalid('*')`로만 막았는데 런타임은 쉼표로 쪼갠 목록을 보므로
  `'https://app.example.com,*'`와 공백이 붙은 `' * '`가 통과한 뒤 **전체 origin 허용**이 됐다.
  파서를 `cors.config.ts`로 옮겨 Joi와 런타임이 같은 함수를 쓰게 하는 것이 해법이다.
- 관측(metric prefix, scrape job/target/path, 대시보드 route 필터)은 `.env`가 아니라
  `config/observability.config.json`에서 관리하고 `yarn generate:observability`로 생성물을 맞춘다.

**DB 교체 지점 (A-3-D)**

- 드라이버 교체는 **`DB_TYPE` 하나로** 한다. 코드를 고치지 않는다.
- 지원 드라이버를 추가할 때는 `database.config.ts`의 `SupportedDbType`,
  `env.validation.ts`의 `valid(...)`, 드라이버 패키지를 **같은 커밋에서** 갱신한다.
- 드라이버 전용 옵션(`schema` 등)과 선택 옵션(`ssl`)은 **해당하지 않으면 값이 `undefined`다.**
  `ssl: false`처럼 끈 상태를 명시하면 드라이버마다 해석이 갈릴 수 있고, 조건부 spread로
  키를 없애면 실제 객체 모양이 코드에서 안 보인다 (A-5).
- **ORM 교체는 이 스위치가 아니다** — `src/common/persistence/`의 어댑터를 교체하는 일이다 (A-1-P).

**TLS 검증을 끄지 않는다 (A-3-S)**

- DB 연결에 TLS를 켜면 **인증서 검증도 켜져 있어야 한다.** `rejectUnauthorized: false`는
  TLS의 두 보장 중 ②신원 확인만 끄기 때문에, 중간자가 아무 인증서로 끼어들어도 연결이 성립한다.
  앱↔공격자, 공격자↔DB 양쪽이 정상 암호화된 상태로 **공격자만 전부 평문으로 본다** —
  DB 비밀번호, 모든 쿼리, 모든 사용자 데이터.
- 이것이 위험한 실질적 이유는 **작동하기 때문**이다. 설정이 귀찮아서 개발 중에 껐다가
  그대로 배포되고, 연결은 되므로 리뷰·모니터링·테스트 어디에도 안 걸린다.
- 관리형 DB는 CA 번들을 공개하므로 `DB_SSL_CA`에 넣어 검증을 켠 채로 붙는다.
- 검증을 끄는 것은 **명시적 옵트아웃**이어야 하고(`DB_SSL_REJECT_UNAUTHORIZED=false`),
  production에서는 `env.validation.ts`가 그 값을 거부한다.

**프록시 뒤에서는 홉 수를 명시한다 (A-3-P)**

- `req.ip`는 기본적으로 TCP 소켓의 상대 주소다. 로드밸런서 뒤에서는 전부 프록시 IP가 되어
  **IP 기준 rate limit이 전 사용자 공용 버킷**이 된다(한 명이 시끄러우면 전원 429).
- 신뢰 홉 수는 배포 토폴로지가 결정하므로 코드가 아니라 `TRUST_PROXY_HOPS`로 둔다.
- **"전부 신뢰"는 지원하지 않는다.** `X-Forwarded-For`는 위조 가능하므로,
  전부 신뢰하면 클라이언트가 매 요청 다른 IP를 주장해 rate limit을 무한 우회한다.
  그래서 이 값은 정수만 받고, 정수가 아니면 무시한다.

### IV. 생성물은 손으로 고치지 않는다 (A-4)

- `ops/prometheus/prometheus.yml`과 `ops/grafana/provisioning/dashboards/json/**`는
  `scripts/generate-observability.ts`가 소유한다. **직접 편집 금지** — 소스는
  `config/observability.config.json`이고, 반영은 `yarn generate:observability`로 한다.
- 이 파일들은 `.prettierignore`에 있다. 포맷터를 다시 걸지 않는다.
  생성기는 `JSON.stringify(..., 2)`로 배열을 펼쳐 쓰는데 prettier는 짧은 배열을 한 줄로 접어서,
  둘 다 걸면 커밋마다 `yarn check:observability`가 stale로 실패하는 왕복이 생긴다.

### V. 객체는 명시적으로 만든다 (A-5)

**객체 spread를 쓰지 않는다.**

```ts
// 금지
const options = { ...base, logging };
const ssl = { ...(ca ? { ca } : {}), rejectUnauthorized };
```

이유는 성능이나 안전성이 아니라 **읽는 흐름**이다. `{ ...base, logging }`을 만나면
"이 객체에 뭐가 들어 있지"를 확인하러 `base`를 찾아가야 하고, `base`가 또 spread면 다시 따라간다.
객체 하나의 모양을 알기 위해 파일을 몇 번 오가는 상태가 되고, **그 왕복이 읽던 흐름을 끊는다.**

`...(cond ? { x } : {})`는 더 나쁘다. 필드가 **있을 수도 없을 수도** 있어서 타입 선언만 봐서는
실제 모양을 알 수 없고, 조건을 따라가야 비로소 알 수 있다.

**대신 쓰는 것**

| 상황                 | 방법                                                                                                                               |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 기본값 + 일부 교체   | 필드를 **전부 적는다.** 공통 부분이 크면 그 모양을 만드는 **함수**를 둔다                                                          |
| 조건부 필드          | 키는 항상 두고 **값에 `undefined`를 넣는다.** 객체 모양이 코드에 그대로 보인다                                                     |
| 만든 뒤 채워야 함    | 객체를 만들고 **조건부로 대입**한다 (`if (x !== undefined) options.x = x`)                                                         |
| 서드파티 표면 재수출 | `Object.assign`을 쓴다 — **우리가 정의한 구조가 아니어서** 필드를 적을 수 없는 유일한 경우다(모듈 mock 등). 근거를 주석으로 남긴다 |

`Object.assign`이 lint를 통과한다는 사실을 우회로로 쓰지 않는다. 위 표의 마지막 줄이 유일한 용도다.

**대상이 아닌 것** — 배열 spread(`[...items]`)와 rest 파라미터·호출 인자(`del(...keys)`).
둘 다 구조를 가리지 않고 타입이 그 자리에 있어서 흐름을 끊지 않는다.

**`eslint.config.mjs`의 `no-restricted-syntax`가 강제한다** (`ObjectExpression > SpreadElement`).

### VI. API 계약 (B-1 ~ B-4)

**라우팅 (B-1)**

- URI 버저닝을 사용한다. 모든 컨트롤러 핸들러에 `@Version('1')`을 명시한다. → `/v1/...`
- 컨트롤러 경로에 `v1`을 직접 쓰지 않는다 (`@Controller('foo')`가 맞고 `@Controller('v1/foo')`는 틀림).

**OpenAPI 문서 (B-2)**

- 문서는 **코드에서 생성한다.** 별도로 관리하는 스펙 파일을 두지 않는다 — 갈라지면 둘 다 못 믿는다.
- 새 엔드포인트는 `@ApiOperation`과 응답 데코레이터를 붙인다. DTO 필드는 `@ApiProperty`로 설명한다.
- 스크랩·헬스체크처럼 문서에 넣을 이유가 없는 라우트는 `@ApiExcludeController()`로 제외한다.
- `APP_SWAGGER_ENABLED=false`로 노출을 끌 수 있다. 스펙이 공개돼도 되는지는 배포 환경마다 다르고,
  **끄는 수단이 없으면 "코드를 고쳐서 배포"가 유일한 방법이 된다.**

**응답 형식 (B-3)**

- 성공 응답은 전역 `ResponseInterceptor`가 `{ code, message, data }`로 감싼다.
  Service/Controller는 **순수 데이터만 반환**하고 봉투를 직접 만들지 않는다.
- 봉투를 우회해야 하는 경우(파일 스트림, Prometheus 텍스트 등)에만 `@RawResponse()`를 쓴다.
  탈출구가 없으면 인터셉터를 우회하는 우회로가 아무 데나 생긴다.
- 에러 응답은 전역 `AllExceptionsFilter`가 동일 형식(`data: null`)으로 만든다.
  Controller에서 에러 응답을 직접 `res.json()`으로 쓰지 않는다.
- 예외는 Nest `HttpException` 계열(`NotFoundException`, `ConflictException` 등)을 던진다.
- **의존 서비스 부재는 503(`ServiceUnavailableException`)이다.** 일반 `Error`를 던지면
  `AllExceptionsFilter`가 500으로 만들어 "서버 버그"로 오인된다.
- 반대로 **호출부의 버그는 500이 맞다.** 포트 계약 위반(`RepositoryContractError`)을
  `HttpException`으로 감싸지 않는 이유가 그것이다 — 그건 클라이언트가 고칠 수 있는 문제가 아니다.

**입력 검증 (B-4)**

- 요청 본문/쿼리는 `class-validator` 데코레이터가 달린 DTO 클래스로 받는다.
- 전역 ValidationPipe가 `whitelist: true`, `forbidNonWhitelisted: true`, `transform: true`로 동작한다.
  → **DTO에 선언되지 않은 필드가 오면 400이다.** DTO를 스펙의 계약으로 취급한다.
- 인터페이스/타입 별칭은 DTO로 쓸 수 없다(런타임에 사라짐). 반드시 클래스.

### VII. 스키마 변경은 마이그레이션으로만 (C-1 ~ C-2)

**스키마 변경 (C-1)**

- `synchronize`는 실제 드라이버에서 **항상 꺼져 있다**. 이 설정을 켜는 변경은 금지한다.
- 스키마 변경은 **오직 마이그레이션으로만** 한다 (`yarn migration:generate` → `yarn migration:run`).
- 생성된 마이그레이션은 **사람이 읽고 검토한 뒤** 커밋한다. 자동 생성물을 그대로 신뢰하지 않는다.
- 이미 배포된 마이그레이션은 수정하지 않는다. 새 마이그레이션을 추가한다.
- 파괴적 변경(컬럼/테이블 삭제, 타입 축소)은 해당 기능의 `plan.md`에 롤백 전략과 함께 명시한다.
- **soft delete를 쓰는 테이블의 유니크 인덱스는 partial로 만든다** (`WHERE deleted_at IS NULL`).
  soft delete는 행을 지우는 게 아니라 컬럼에 시각을 적는 것이라, 일반 유니크 인덱스는
  **삭제된 행까지 포함해서** 막는다. "탈퇴한 이메일로 재가입 불가", "지운 슬러그 재사용 불가"가
  이렇게 생긴다. 경합 없이 100% 재현되는데, 탈퇴 기능이 생기기 전에는 드러나지 않는다.
  - partial로 만드는 것 자체가 **"삭제된 값의 재사용을 허용한다"는 제품 결정**이므로
    그 기능의 `plan.md`에서 정한다. 조건 없이 붙이지 않는다.
  - 새 테이블 체크리스트 항목이다 — 유니크 제약과 soft delete가 함께 있는 모든 테이블에서
    반복된다(이메일, 조직명, 초대코드, 슬러그).

**테스트 DB (C-2)**

- E2E는 docker-compose의 실제 PostgreSQL에서 돌아간다. 운영 기본 드라이버의 SQL 번역,
  제약조건, 드라이버 에러 변환을 인메모리 대역으로 가리지 않는다.
- 테스트 픽스처 전용 테이블에만 `synchronize: true`를 허용한다. 운영 엔티티와 마이그레이션은
  계속 C-1을 따른다.

### VIII. 테스트 동반 (D-1 ~ D-3) — NON-NEGOTIABLE

**필수 동반 테스트 (D-1)**

- 새 Service / **Repository** / 포트 어댑터 / Util / Interceptor / Filter / Guard →
  같은 디렉토리에 `*.spec.ts` 동반. **예외 없음.**
- **포트 어댑터 테스트는 번역을 단언한다.** 중립 조건이 어떤 ORM 옵션으로 바뀌는지가
  이 계층의 계약이다 (배열 → `IN`, `null` → `IS NULL`, `select` 전달, 방향 대문자화).
- **도메인 Repository 테스트는 `IRepository<T>`를 mock하고 넘긴 조건을 단언한다** —
  정규화된 값이 들어갔는지, `select`에 필요한 컬럼이 있는지. 그게 이 계층이 지키는 계약이다.
- 새 HTTP 엔드포인트 → `test/*.e2e-spec.ts`에 성공 케이스 1개 + 실패 케이스 1개 이상 추가.

**mock이 증명할 수 없는 것은 실제 DB로 확인한다 (D-1-M)**

mock은 **넘긴 인자**를 단언할 수 있을 뿐, **그 인자를 받은 쪽이 실제로 무엇을 하는지**는 증명하지 못한다.
아래는 mock 기반 단위 테스트에 두면 통과하지만 아무것도 검증하지 않는다 — `test/*.e2e-spec.ts`가 맡는다.

- ORM/DB의 의미론에 의존하는 동작: `insert`가 덮어쓰는지, 빈 `patch`에서 무슨 일이 나는지,
  `select: false` 컬럼이 실제로 감춰지는지, `IS NULL` / `IN` 번역이 의도한 SQL이 되는지
- DI 배선: 토큰·프로바이더·`forFeature`가 실제로 조립되는지

판별법: **"구현을 통째로 mock으로 바꿔도 이 테스트가 통과하는가?"** 통과한다면 그 테스트는
mock을 테스트하고 있다 (D-2의 마지막 항목).

**금지 패턴 (D-2)**

다음은 완료의 증거가 아니라 **블로커**다. 발견되면 태스크는 미완료다.

- `it.skip` / `describe.skip` / `.only`
- `// TODO` 로 남긴 미구현 분기
- 단언 없는 테스트 (`expect` 없이 호출만 하는 것)
- 검증 대상 로직 자체를 통째로 mock해서 사실상 mock을 테스트하는 것

**완료 게이트 (D-3)**

기능이 "완료"이려면 아래가 **전부** 통과해야 한다.

```bash
yarn lint
yarn typecheck
yarn test
yarn test:e2e
yarn check:observability   # observability 관련 변경이 있었을 때
```

통과 로그 없이 완료를 선언하지 않는다.

### IX. 관측 가능성 (E-1)

- 로깅은 `nestjs-pino` Logger를 주입받아 쓴다. `console.log` 금지.
- 로그에 **비밀정보를 남기지 않는다**: 비밀번호, 토큰, 세션 식별자 원문, 인증 헤더, 개인정보.
- 새 백그라운드 잡 / 외부 호출을 추가하면 실패가 관측 가능한지 확인한다
  (에러 로그 또는 metric 중 최소 하나).
- **헬스체크 항목을 조건부로 제외하지 않는다.** 비활성화된 의존성은 목록에서 빼는 것이 아니라
  `down` 상태로 보고한다. 항목이 사라지면 헬스체크는 초록불인데 기능은 죽어 있는 상태가 만들어지고,
  k8s readiness가 통과해 트래픽이 계속 들어온다. Prometheus에서도 게이지가 `0`이 아니라
  아예 없어져서 알람 룰이 발동할 대상을 잃는다.
- 종료 경로도 관측 대상이다. graceful shutdown은 **타임아웃과 함께** 구현하고,
  드레인 시작·완료·타임아웃을 각각 로그로 남긴다.
- **정상 종료 경로에서 `process.exit()`을 부르지 않는다.** pino transport는 워커 스레드에서
  비동기로 flush하는데 `exit()`은 그 큐를 기다리지 않아서 **방금 남긴 종료 로그가 유실된다** —
  배포 실패를 사후 분석할 때 가장 필요한 줄이 그것이다. `process.exitCode`만 정하고
  이벤트 루프가 비면 자연 종료되게 둔다. 강제 종료(타임아웃)는 정의상 하드 킬이라 예외다.
- **요청 식별자는 응답 헤더로도 내보낸다** (`X-Request-Id`). 로그에만 남기면 클라이언트가 받은
  에러와 서버 로그를 연결할 수단이 없다. 들어온 헤더가 있으면 이어받는다 — 상위 서비스가 부여한
  ID를 버리면 분산 추적이 요청마다 끊긴다. CORS `exposedHeaders`에 올려두기만 하고 아무도
  설정하지 않으면 값은 항상 `undefined`다(설정만 있고 동작은 없는 상태).
- **로그를 거르는 경로는 상수에서 파생시킨다.** 헬스체크·scrape처럼 노이즈를 만드는 경로를
  제외할 때 **버저닝 prefix까지 포함한 실제 경로**여야 한다. 컨트롤러 경로만 적으면
  (`'/health'` vs 실제 `/v1/system/health`) 필터가 **조용히 아무것도 안 하고** 하루 수천 줄이
  그대로 쌓인다. 경로 문자열을 두 곳에 손으로 적지 않는다.
- **응답이 이미 시작된 뒤에는 에러 응답을 쓰지 않는다.** 헤더가 나간 상태에서 `status()`를
  다시 부르면 `ERR_HTTP_HEADERS_SENT`가 나고 **진짜 원인이 그 에러에 가려진다.**
  전역 예외 필터는 `headersSent`를 확인하고, 그 경우 로그만 남긴다.
- **조용히 실패하는 API를 남겨두지 않는다.** 에러 없이 항상 0건을 처리하는 함수는
  버그보다 나쁘다 — 나중에 누가 "있으니까 동작하겠지" 하고 보안 관련 경로(일괄 로그아웃,
  캐시 무효화)에 쓰면 처리했다고 믿는 상태가 만들어진다. 고칠 수 없으면 **지운다.**

### X. 저장소 간 쓰기 순서 (G-1)

한 요청이 서로 다른 저장소(RDB / Redis)에 쓸 때는 **트랜잭션으로 묶을 수 없다.**
중간에 실패하면 반쯤 진행된 상태가 반드시 남는다. 없앨 수 없으므로 **남았을 때 덜 아픈 순서**를 고른다.

- **기존 상태를 파괴하는 쓰기를 마지막에 둔다.** 키 삭제, 기존 레코드 교체가 여기 해당한다.
- 앞선 쓰기는 실패해도 피해가 작은 것(통계·감사용 필드 갱신 등)부터 배치한다.
- 판별법: "이 쓰기까지 성공하고 다음 쓰기가 실패하면, 사용자에게 무엇이 남는가?"
  답이 **"요청은 실패했는데 기존에 되던 것이 깨졌다"**면 순서가 틀린 것이다.
- 저장소가 둘 이상인 흐름을 새로 만들면 `plan.md`에 **쓰기 순서와 그 근거**를 적는다.

### XI. 트랜잭션 경계 (H-1)

트랜잭션 경계는 **Service가 정한다**(A-1). Repository는 자기 메서드 안에서 완결되는 쓰기만 한다.

**TypeORM은 세션/유닛오브워크 ORM이 아니다.** Hibernate나 EF Core처럼 변경을 추적했다가
커밋 시점에 flush하지 않는다. 이 차이가 실무에서 가장 많이 오해되는 지점이라 명시한다.

- `repository.create()`는 **DB를 건드리지 않는 동기 인스턴스 생성**이다. "세션에 스테이징"이 아니다.
- `repository.save()`는 **호출 즉시 커밋**된다.
- 따라서 `create()`와 `save()`를 나눠 써도 **트랜잭션은 생기지 않는다.**
- 바깥 트랜잭션에 자동으로 합류하지도 않는다.

**현재 이 스캐폴드에는 트랜잭션 인프라가 없다.** 포트(`IRepository<T>`)에 트랜잭션 API가 없는 것도
의도된 것이다 — `EntityManager`를 포트에 노출하면 그것 자체가 "TypeORM을 다시 export하는 것"이 되어
포트의 목적(ORM 교체 가능성)이 사라진다. 그래서 규칙은 다음과 같다.

- 한 요청이 **같은 DB의 여러 테이블에 쓰는 흐름을 만들지 않는다.**
- 필요해지는 순간, 그 기능의 `plan.md`에서 **먼저 방식을 정하고 도입한다.** 채택 예정안은
  `typeorm-transactional`(AsyncLocalStorage 기반 `@Transactional()`)이다. **어댑터와 포트
  시그니처를 바꾸지 않고** Service가 경계를 선언할 수 있는 유일한 선택지라서다.
- Service가 `DataSource` / `EntityManager`를 직접 잡는 방식은 **쓰지 않는다.** A-1-R과 충돌한다.
- 도입 전까지 이 조항은 **"아직 못 하는 것"의 선언**이다. 우회하지 말고 여기부터 고친다.

저장소가 서로 다르면(RDB / Redis) 트랜잭션 자체가 불가능하다 → G-1을 따른다.

## 의도적 비범위

이 스캐폴드가 **일부러 안 하는 것**들. 되살리려면 이 문서를 먼저 고쳐야 한다.

- **도메인 모듈** — auth, user를 포함해 어떤 업무 도메인도 여기 두지 않는다.
  admin 앱이 필요하면 파생 프로젝트에서, user 앱이 필요하면 또 다른 파생 프로젝트에서 확장한다.
  **이 저장소가 admin/user 둘 다를 runtime으로 품지 않는 것**이 핵심이다.
- **인증·인가 구현** — 위와 같은 이유. Swagger의 인증 스킴 선언도 실제로 쓰이기 전까지 넣지 않는다.
- **제네릭 Repository를 Service에 노출하기** — A-1-P 참고. 포트는 ORM 교체를 위한 것이고
  호출 편의를 위한 것이 아니다. `IRepository<T>`를 Service가 직접 주입받는 구조는 금지다.
- **포트에 연산자 추가** — 범위·부분일치·OR·조인. 필요하면 어댑터에 이름 있는 메서드를 만든다.
- **ORM 자동 스키마 동기화** — C-1 참고.
- **트랜잭션 인프라** — H-1 참고. 안 하는 것이 아니라 **아직 안 한 것**이며, 도입 조건이 정해져 있다.

## Development Workflow

### 명세 우선 (F-1)

- 새 기능은 **명세 → 계획 → 태스크 → 구현** 순으로 진행한다. 앞 단계 산출물 없이 뒤 단계로 넘어가지 않는다.
  산출물은 기능당 디렉토리 하나(`specs/NNN-<slug>/`)에 `spec.md` / `plan.md` / `tasks.md`로 쌓인다.
- **명세에 없는 것을 구현하지 않는다.** 구현 중 필요해지면 명세를 먼저 고친다.
- `spec.md`에 미해소 질문(`[NEEDS CLARIFICATION: ...]`)이 남아 있으면 `plan.md`로 넘어가지 않는다.
- `plan.md` / `tasks.md`가 마음에 안 들면 그 파일을 직접 고치지 말고 **명세 단계로 되돌아가**
  스펙을 재정의한다. 문서 간 일관성이 깨지는 것이 개별 문서의 완성도보다 비싸다.

각 단계를 실행하는 구체적인 커맨드는 `CLAUDE.md`에 있다. 도구가 바뀌어도 위 순서와 산출물은 바뀌지 않는다.

### 커밋 (F-2)

- Conventional Commits를 따른다 (commitlint가 강제). `feat:`, `fix:`, `refactor:`, `test:`, `chore:`, `docs:`
- 커밋은 `tasks.md`의 태스크 단위로 원자적으로 만든다.
- pre-commit 훅이 `lint-staged`(eslint --fix + prettier)를 돌린다. 훅을 `--no-verify`로 우회하지 않는다.

### 범위 통제 (F-3)

- Plan 단계에서 정해진 파일 목록 밖을 건드려야 하면, 먼저 `plan.md`를 갱신한다.
- 리팩터링은 기능 구현과 **분리된 커밋**으로 한다.

### SDD를 쓰지 않는 범위 (F-4)

모든 변경에 파이프라인을 태우지 않는다. 절차가 모든 변경에 걸리면 절차 자체가 우회된다.

- 오타 수정, 주석/문서 수정, 포맷팅
- 기존 동작을 바꾸지 않는 로그 메시지 조정
- 의존성 버전 범프(동작 변경 없음)

**새 엔드포인트, 새 엔티티/마이그레이션, 새 환경변수, 계층 경계 변경**이 하나라도 포함되면
반드시 명세 단계부터 시작한다.

## Governance

- 이 문서는 다른 모든 관행에 우선한다. `CLAUDE.md`와 충돌하면 이 문서가 이긴다.
  - 역할 분담: `CLAUDE.md`는 도구·환경·실행 방법, 이 문서는 설계 원칙과 품질 기준.
  - 판별법: **"도구를 바꿔도 이 문장이 그대로인가?"** 그렇다면 이 문서, 아니면 `CLAUDE.md`.
- 규칙 변경은 코드보다 이 문서를 먼저 고치고, `constitution-history.md`에 **이유와 함께** 남긴다.
  이력의 값은 "언제 바꿨나"가 아니라 **"왜 그때 그렇게 판단했나"**에 있다.
  - 이력을 별도 파일로 둔 이유: 원칙은 매 세션 읽히고 이력은 "이 규칙 왜 이래?"를 물을 때만 열린다.
- 버전 규칙: MAJOR = 기존 규칙 삭제/역전, MINOR = 원칙 추가 또는 구조 변경,
  PATCH = **규칙의 해석이 달라지는** 표현 정정.
- **규칙이 바뀌지 않는 수정은 버전을 올리지 않고 이력도 남기지 않는다.** 그냥 겹쳐쓴다 —
  오타, 마크다운 렌더링, 표 정렬, 링크 수정 등. 남길 "이유"가 없는 변경으로 이력을 채우면
  의미 있는 항목의 신호가 죽는다. A-1-W가 코드에서 말한 것과 같은 실패다.
- `spec.md` / `plan.md` / `tasks.md`는 이 문서를 기준으로 모순·누락 검사를 받는다.
  원칙을 추가할 때는 **검사 가능한 문장**으로 쓴다 ("잘 작성한다" 같은 문장은 검사되지 않는다).
- **파생 프로젝트는 이 문서를 복사한 뒤 자기 것으로 고친다.** 도메인 규칙, 인증 정책,
  선택한 DB의 세부 조항이 거기서 추가된다. 그 추가분을 이 저장소로 되돌리지 않는다.
